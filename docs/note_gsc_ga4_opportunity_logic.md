# Google Search Console / GA4 の数字を「改善候補」に変えるまで

`Google Search Console` や `Google Analytics 4` を見れば、数字自体は取れます。  
でも実際に困るのは、「で、今週どの記事を直せばいいのか」がすぐに分からないことでした。

今回作ったのは、`yoshilover.com` 向けの SEO 分析アプリです。  
目的は、`Google Search Console` と `Google Analytics 4` の日次データをためて、毎週の手集計をやめることでした。

単にダッシュボードを作るだけではなく、最終的には次の 4 種類の「改善候補」を自動で出すところまでを MVP にしました。

- 順位下落
- 伸びた記事
- リライト候補
- カニバリ候補

この記事では、`GSC/GA4` の数字をどうやって「改善候補」に変えたかをまとめます。

## まず困っていたこと

SEO の数字は、見る場所が多いです。

- `Google Search Console` では `clicks / impressions / ctr / position`
- `Google Analytics 4` では `sessions / users / key events`

しかも、判断したい単位も 1 つではありません。

- サイト全体
- 記事別
- クエリ別
- カテゴリ別

この状態だと、毎週やることはだいたい同じです。

1. `GSC` で順位が落ちたページを探す
2. `GA4` で流入も落ちているかを見る
3. 逆に伸びた記事も見つける
4. CTR が低い記事や、複数ページに分散しているクエリを拾う

これを毎回手でやるのは、普通に面倒です。  
なので今回は、数字を見るアプリではなく、「次に触る候補を出すアプリ」に寄せました。

## 生データのままでは使いにくい

今回のデータフローはかなり単純です。

1. `Cloud Run Jobs` で日次 batch を実行
2. `Google Search Console API` と `Google Analytics Data API` からデータ取得
3. `BigQuery raw` に保存
4. 画面用の mart を作る
5. Web アプリからその mart を読む

大事だったのは、いきなり画面ごとの query を増やさないことでした。

`raw_gsc` と `raw_ga4` はあくまで保存用です。  
画面や改善候補の判定にそのまま使うと、条件の置き場所が散らかります。

そこで、まず中間の参照面を切りました。

- `page_daily`
- `query_daily`
- `category_daily`
- `improvement_candidates_base`

このうち改善候補の中心になったのが、`improvement_candidates_base` です。

## まずは比較に必要な列を 1 つの view に集めた

改善候補を出したいとき、毎回必要になる情報はかなり似ています。

- 今週のクリック数
- 前週のクリック数
- 今週の表示回数
- 前週の表示回数
- CTR の差分
- 平均順位の差分
- セッションの差分
- いま何ページに分散しているか

これを画面ごとに個別実装すると、あとで必ずズレます。  
なので先に `improvement_candidates_base` という view を作り、`current_7d` と `previous_7d` の比較列をまとめて持たせました。

設計としてはこんなイメージです。

```text
reference_end_date
entity_type
entity_key
current_clicks / previous_clicks / clicks_delta
current_impressions / previous_impressions / impressions_delta
current_ctr / previous_ctr / ctr_delta
current_position / previous_position / position_delta
current_sessions / previous_sessions / sessions_delta
current_support_count / previous_support_count
```

この段階では、まだ「どれを改善候補にするか」は決めません。  
まずは比較しやすい形に揃えることを優先しました。

これでよかったのは、判定ロジックの変更先が 1 か所減ったことです。  
「順位下落の条件を少し厳しくしたい」と思ったときも、view の上で作った consumer 側の条件を直せば済みます。

## 改善候補は 4 種類に分けた

今回の MVP では、改善候補を次の 4 種類に分けました。

## 1. 順位下落

単にクリックが落ちたページではなく、「検索順位が悪化したページ」を優先して拾うようにしました。

条件はこうです。

- 前週の `impressions >= 50`
- 前週平均順位が `20` 位以内
- `position_delta >= 1.0`
- さらに `clicks` または `sessions` が `20%` 以上かつ `3` 以上落ちている

ここで大事なのは、`position_delta >= 1.0` を必須にしたことです。  
需要そのものが減っただけのページまで「順位下落」に混ぜると、打ち手がブレます。

## 2. 伸びた記事

これは逆で、「今伸びているページ」を見つけるルールです。

- 今週の `impressions >= 50`
- 今週平均順位が `20` 位以内
- `clicks` または `sessions` が `20%` 以上かつ `3` 以上伸びている
- さらに `position` 改善、または `impressions` 増加がある

伸びている記事は、そのままにするより、内部リンクやタイトル調整でさらに伸ばせることがあります。  
「問題を探す」だけでなく「勝ち筋を増やす」候補として分けました。

## 3. リライト候補

これは「見られているのに取り切れていない記事」です。

- 今週の `impressions >= 80`
- 平均順位が `6-20` 位
- `CTR < 12%`

1 位や 2 位なら CTR が低くても別の事情がありえますし、30 位台だとそもそも露出不足です。  
そこで、`6-20` 位くらいの中位記事に絞りました。

このルールで拾いたかったのは、本文リライトだけではありません。

- タイトル修正
- description 見直し
- 見出しの再構成
- 競合と比べた検索意図のズレ確認

など、「手を入れると変わりやすいページ」を優先的に見るための候補です。

## 4. カニバリ候補

カニバリは `page` ではなく `query` 単位で見ています。

- 今週 `2` ページ以上に分散
- `impressions >= 80`
- 平均順位 `20` 位以内

複数ページに露出が割れているクエリを拾うことで、統合、役割分担、内部リンク整理の候補にできます。

ここは `query_daily` と、query が今週何ページに出ているかの `support_count` が効きました。  
「1 記事の成績」ではなく「同じクエリをサイト内でどう奪い合っているか」を見るためのルールです。

## ポイントは、AI スコアではなく説明できるルールにしたこと

今回の MVP では、あえて複雑なスコアリングをしていません。

理由は 2 つあります。

1. 自分で見直せること
2. 閾値の調整がしやすいこと

たとえば「なぜこのページが順位下落に入ったのか」が説明できないと、あとでルールを直せません。

一方で、

- 前週表示が 50 以上だった
- 前週 20 位以内だった
- 今週は順位が 1 以上悪化した
- クリックも 20% 以上落ちた

と分かれば、判定の理由は明快です。

MVP の段階では、まずこの「説明できること」を優先しました。

## 実データでは、比較期間が足りない問題も出た

実装してすぐに気づいたのは、ルールを作っても、データがまだ十分たまっていないと比較できないことでした。

今回の比較は `current_7d vs previous_7d` なので、少なくとも `14日` 分のデータが必要です。  
でも初期フェーズでは、当然そこまでたまっていません。

ここで雑に実装すると、画面には「候補 0 件」と出てしまいます。  
でも実際には 0 件ではなく、「まだ比較できない」だけです。

この違いはかなり重要でした。

なので UI では、

- 比較 ready
- まだ `14日` 蓄積中
- `14日` はあるが前週比較列は未生成

を分けて扱うようにしました。

さらに `npm run data:readiness` という確認 script も作って、

- raw の最新日
- mart の最新日
- `page_daily` の active days
- `improvement_candidates_base` の前週比較 ready 状態

を 1 回で見られるようにしました。

これは地味ですが、運用ではかなり効きます。  
「候補が出ない理由」を、画面ではなくデータ面から先に切り分けられるからです。

## 今回やってよかった設計

今回の実装で、あとから効いているのは次の 3 つです。

- `raw` と `mart` を分けたこと
- 改善候補の前段を `improvement_candidates_base` にまとめたこと
- 判定ルールを `rank_drop / growth / rewrite / cannibal` ごとに分けたこと

この構成にしておくと、

- 閾値を少し変える
- 画面説明を更新する
- ダッシュボードと一覧画面で同じルールを使う

といった変更がやりやすいです。

逆に、最初から複雑なスコアを 1 本で作っていたら、たぶん調整しづらかったと思います。

## まとめ

`Google Search Console` と `Google Analytics 4` の数字は、見えるだけでは足りません。  
本当に欲しいのは、「次にどれを触るか」が分かる状態です。

そのために今回やったのは、

1. `raw` をためる
2. 画面用の mart を作る
3. `current_7d / previous_7d` の比較 view を作る
4. 説明可能なルールで改善候補に落とす

という、かなり地味な分解でした。

でも SEO の運用では、こういう地味な整理の方が長持ちします。

次は、実データが十分たまった段階で、

- 候補件数が多すぎないか
- `growth` と `rewrite` が重なりすぎないか
- `rank_drop` の閾値が厳しすぎないか

を見ながら、実運用に合わせて微調整していく予定です。
